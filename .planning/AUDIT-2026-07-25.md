## 2. Security — must fix before this goes anywhere real

### S1 (CRITICAL) — Service-role key is named `NEXT_PUBLIC_*`

`src/lib/supabase/admin.ts:7` reads `process.env.NEXT_PUBLIC_SUPABASE_SECRET_KEY`.

Next.js inlines every `NEXT_PUBLIC_`-prefixed variable into any bundle that references it. Today
`admin.ts` is imported only from server files, so the key is probably not in the browser bundle — but
it is one careless import away from being published to every visitor, and hosting dashboards treat
`NEXT_PUBLIC_*` as client-safe by policy.

Fix: rename to `SUPABASE_SECRET_KEY` (no prefix), rotate the key, and add a build-time guard that
throws if the secret is read outside a server context.

### S2 (CRITICAL) — Task server actions have no authorization at all

`src/app/tasks/actions.ts` — `completeTask`, `updateTask`, `reorderTask`, and
`createTaskWithSubtasks` use the service-role client and never call `supabase.auth.getUser()`.
They accept a caller-supplied `taskId` / `memberId` / `workspaceId` and act on it unconditionally.

Failure scenario: any authenticated user posts a server action with a UUID belonging to another
household's task and completes, retitles, reassigns, or reorders it. Nothing in the DB or the app
stops it — RLS is bypassed by the admin client, and there is no app-level check to replace it.

Compare `src/app/workspaces/actions.ts`, which does check `getUser()` and scopes deletes to
`user.id`. The task actions simply never got the same treatment.

### S3 (CRITICAL) — RLS was disabled rather than fixed

`supabase/migrations/006_fix_task_rls.sql` replaced the real `tasks_insert` and
`task_assignments_insert` policies with `WITH CHECK (auth.uid() IS NOT NULL)`, with the comment
"Security is enforced at the server action layer". Per S2, it is not enforced there either.

Result: any logged-in user can insert a task into any workspace, and insert a `task_assignments` row
naming any `member_id`.

**Root cause** — `workspace_members_select` (migration 002) is self-referential:

```sql
CREATE POLICY "workspace_members_select" ON workspace_members
FOR SELECT USING (
  workspace_id IN (SELECT workspace_id FROM workspace_members WHERE auth_user_id = auth.uid())
);
```

Evaluating the policy requires reading `workspace_members`, which re-triggers the policy → Postgres
`42P17` infinite recursion. Every downstream policy that joins `workspace_members` inherits it. Each
recursion error was then worked around by swapping in the admin client, which is why the service-role
client now appears in `page.tsx` and both action files.

**Correct fix** — break the recursion with a `SECURITY DEFINER` helper, which runs with the owner's
rights and therefore does not re-enter RLS:

```sql
CREATE FUNCTION public.is_workspace_member(ws uuid)
RETURNS boolean LANGUAGE sql SECURITY DEFINER STABLE
SET search_path = public AS $$
  SELECT EXISTS (
    SELECT 1 FROM workspace_members
    WHERE workspace_id = ws AND auth_user_id = auth.uid()
  );
$$;
```

Then rewrite the policies in terms of `is_workspace_member(...)` / an equivalent
`is_task_assignee(task_id)`, and delete the admin client from the read path. `SET search_path` is
required — a `SECURITY DEFINER` function without it is itself a privilege-escalation vector.

### S4 (HIGH) — No input validation at the trust boundary

Server actions take raw strings and arrays straight from the client. No length caps on `title` /
`description`, no UUID-format check on ids, no cap on the `subtasks` array, no verification that
`memberIds` belong to `workspaceId`. That last one is what lets a caller assign a task to an
arbitrary member row. A `zod` schema per action, parsed as the first statement, closes S4 and gives
S2 somewhere natural to live.

## 3. Correctness

- **C1 (HIGH) — silent failures.** `completeTask`, `deleteTask`, `updateTask`, and `reorderTask`
  ignore the `{ error }` field on every mutation. A failed delete returns success, `revalidatePath`
  fires, the row reappears on refresh, and the user is told nothing. Already recorded as a carry-over
  concern in `STATE.md`; still open.
- **C2 (MEDIUM) — `completeTask` parent logic is inverted for the common case.** It marks the parent
  complete when the *child's* siblings are all done, but completing a *parent* directly does not
  complete its children — so `docs/product.md`'s "a task is completed when the entire task and all
  its subtasks are complete" only half-holds. The UI compensates by disabling the parent's complete
  button while any subtask is open, which means a parent with subtasks can never be completed by any
  other route.
- **C3 (MEDIUM) — sort-key generation is global, not per-workspace, and racy.** `max + 1000` read
  then written non-atomically; two concurrent creates collide. Also N+1: one SELECT + one INSERT per
  member per subtask. Replace with a single `INSERT ... SELECT` computing the key in SQL.
- **C4 (LOW) — no `error.tsx` / `loading.tsx` anywhere.** A throw in `page.tsx` gives the default
  Next error screen; the whole tasks page has no streaming fallback.
- **C5 (LOW) — build artifacts committed.** `tsconfig.tsbuildinfo`, `supabase/.temp/cli-latest`, and
  a `.claude/worktrees/` gitlink are tracked. Add to `.gitignore` and `git rm --cached`.
- **C6 (LOW) — `npm run lint` is dead.** `next lint` was removed in Next 16; migrate to
  `eslint .` with a flat config.

## 4. Frontend

The existing design system is genuinely good and should be kept: a coherent warm token set in
`globals.css` (`#FAF9F7` bg, `#7C5CBF` accent, three-step radius and shadow scale), Inter via
`next/font`, hand-drawn empty-state illustration, correct mobile-first split (tab strip < `md`,
sidebar ≥ `md`). Running `ui-ux-pro-max --design-system` proposed a blue/orange + Lora/Raleway system
instead; that is a worse fit for "warm household" than what is already built, so the recommendation
is to **extend these tokens, not replace them**.

Against the skill's CRITICAL/HIGH checklist:

| # | Finding | Sev |
|---|---|---|
| U1 | **Touch targets far below 44px.** The complete / edit / delete controls in `task-card.tsx` are bare 14–18px SVGs with no padding or `hitSlop`. On the primary mobile surface, delete sits ~4px from edit. | CRITICAL |
| U2 | **No focus-visible styling on any button or link.** Focus rings exist on inputs only (`login-card`, both modals, `profile`). Every icon button, sidebar link, tab pill, and modal close is invisible to keyboard focus. | CRITICAL |
| U3 | **Modals are not dialogs.** No `role="dialog"`, `aria-modal`, focus trap, initial focus, Escape-to-close, or focus restore in `new-task-modal.tsx` / `edit-task-modal.tsx`. | CRITICAL |
| U4 | **Toaster is silent to screen readers** — no `aria-live` / `role="status"` in `toaster.tsx`. | HIGH |
| U5 | **Dead navigation.** The All / Household / Work pills in `layout.tsx:44-54` are `<button>`s with no handler — decorative, and they duplicate the sidebar's real filters. The nav also renders Tasks/Workspaces links on `/login` for signed-out visitors. | HIGH |

## 5. Recommended order of work

Each step is a vertical slice per `docs/workflow.md` (schema → RLS → action → UI → tests).

**Step 1 — Close the security holes.** One phase, non-negotiable before any feature work.
1. Rename `NEXT_PUBLIC_SUPABASE_SECRET_KEY` → `SUPABASE_SECRET_KEY`, rotate the key. (S1)
2. Add migration `007`: `is_workspace_member()` / `is_task_assignee()` as `SECURITY DEFINER STABLE
   SET search_path`, rewrite policies `002`/`003`/`006` in terms of them. (S3)
3. Drop the admin client from `page.tsx` and the task read path; confirm the recursion is gone. (S3)
4. Add `getUser()` + zod parse as the first lines of every task action. (S2, S4)
5. Tests: a non-member calling `completeTask` / `updateTask` / `deleteTask` on someone else's task
   must fail — these tests fail today.

**Step 2 — Make failures visible.** Return `{ ok, error }` from every action, surface via the
existing toaster, roll back optimistic state on error, add `error.tsx` + `loading.tsx`. (C1, C4)

**Step 3 — Accessibility and mobile pass.** U1–U4 first (all CRITICAL/HIGH and all cheap): pad icon
buttons to 44px, add a shared `focus-visible` ring token, make the modals real dialogs, add
`aria-live` to the toaster. Then U5 (delete the dead pills, hide nav when signed out) and U7.

**Step 4 — Ship drag-to-reorder.** Highest-value unbuilt spec feature, and the backend already
exists. Wire `@hello-pangea/dnd` to `reorderTask`; fix C3's key generation first; provide the
keyboard alternative the DnD-accessibility guideline requires.

**Step 5 — Task updates + speech-to-text.** `task_updates` CRUD, then the Web Speech API at the
input layer only. Audio must never be persisted.

**Step 6 — Recurring tasks.** `task_rules` UI + a pg_cron generator. Design idempotently: the
generator must be safe to run twice for the same `next_run_at`.

**Step 7 — Design polish.** Dark mode via a second `@theme` block (U6), semantic tokens for deadline
and toast surfaces (U10), `lucide-react` migration (U11), reduced-motion guard (U8), skeletons (U12).

Steps 1 and 2 fix defects and should land before 3–7. Step 3 is small enough to fold into the same
week. Note that Step 1's migration will conflict with any concurrent schema work, so it should go
first regardless of priority ordering.

**Also worth doing at some point:** reconcile `.planning/STATE.md` with the three off-workflow
commits so the GSD state stops drifting, and fix `npm run lint` (C6) so CI has a working lint gate.
