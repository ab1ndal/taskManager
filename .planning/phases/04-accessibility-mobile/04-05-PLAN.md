<objective>
Close the touch-target audit gap (U1) and replace `window.confirm` with an in-app dialog (part of
U3, per CONTEXT.md D-04/D-06/D-08), both scoped to `task-card.tsx` and a new
`delete-confirm-dialog.tsx`. This is the second Wave 2 plan depending on `Dialog` from 04-01; it
shares no files with 04-04 (the task-modal conversion), so the two run in parallel.

Purpose: Every icon button on the task card is a bare 14-18px SVG with no padding, well under the
44px WCAG 2.5.5 AAA minimum CONTEXT.md D-01/D-02 adopts. Subtask toggles are the same size and are
frequently missed in audits (RESEARCH.md Pitfall 2) — this plan explicitly covers them. Generic
aria-labels ("Mark complete" × N cards) give screen reader users no way to distinguish tasks in
list-navigation mode. `window.confirm` blocks the main thread, can't be styled, and is suppressible
in some mobile browsers — CONTEXT.md D-04 replaces it with a dialog built on the same primitive as
the task modals.
Output: `task-card.tsx` with 44px hit areas and task-scoped labels on all four button types; a new
`delete-confirm-dialog.tsx` wired in place of `window.confirm`.
</objective>

<threat_model>
## Trust Boundaries

`taskId` and `title` rendered into aria-labels already flow from server-authorized queries elsewhere
in the app (RLS-scoped task rows, per Phase 3) — this plan does not introduce a new read path, and
React's text-node rendering escapes the title string in both the visible label and the aria-label
attribute, so no injection risk from a task title containing markup-like characters. The delete
confirm dialog does not change what `deleteTask` is authorized to do — `deleteTask(taskId)` is called
with the same `taskId` and passes through the same server-side authorization check established in
Phase 3 (`requireUser()` + per-row authorization); this plan only adds a confirmation step before
that call fires.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Tampering | Confirm dialog bypass (e.g. rapid double-click) | accept | `deleteTask` is idempotent from the caller's perspective (a second call on an already-deleted row returns a normal not-found/ok-false result, handled by the existing `runAction` error-toast path) — no new inconsistent state possible. |
| T-04-07 | Repudiation | Accidental deletion via mis-tap | mitigate | This entire plan's purpose (D-04/D-08) — Cancel-first focus and an explicit second tap replace the single-tap `window.confirm`, directly reducing accidental deletes rather than merely logging them. |

No Spoofing/Information-Disclosure/DoS/Elevation vectors — no new input path, no new server call
signature, authorization unchanged from Phase 3.
</threat_model>
