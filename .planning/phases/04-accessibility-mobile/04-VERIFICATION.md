| 1 | Keyboard walk + focus containment | U3 | jsdom `HTMLDialogElement`/top-layer stacking is incomplete (jsdom#3294) — cannot prove focus never escapes | Automated via Playwright (real Chromium, not jsdom) against an isolated test user/workspace on the hosted DB. Opened new-task modal, edit-task modal, and delete-confirm dialog; tabbed 25x forward and backward in each. | ✅ pass (2026-07-26). Focus never reached a real control behind any dialog (nav links, sidebar) in either direction; Escape closed each and returned focus correctly; delete-confirm's first tab stop was Cancel, not Delete. **Noted, not blocking:** in all three dialogs, tabbing past the last focusable element (or Shift+Tab past the first) transiently lands on `<body>` for one keypress before wrapping back inside — a native `<dialog>` quirk. `<body>` has no focus ring and isn't interactive, so it isn't reachable/actionable by a keyboard user, but it's a real deviation from "focus cycles only inside the modal." Not filed as a bug; see script at bottom of this doc if revisiting. |
| 2 | Screen reader announces both toast politeness levels | U4 | Announcement timing/interruption is assistive-tech behavior, not DOM state jest-axe can assert | Playwright proxy (not a substitute for real AT): asserted `role`/`aria-live` on both toast containers and success-toast auto-dismiss (~3.5s); asserted the fix for the found bug below. | ✅ pass (2026-07-26), after a fix — see below. Success toast: `role="status" aria-live="polite"`, auto-dismisses. Client-side validation errors (title too long, etc.) no longer go through the toaster at all — see fix. Real screen-reader announcement timing/interruption for the surviving toast paths (success, server-side action failures) still needs an actual AT pass — not verified here, no automated substitute exists for it. |
| 2b | *(sub-finding, not a checklist row)* — error-toast interaction while a dialog is open | — | — | Original test instructions said "force an error (e.g. submit an edit with an emptied title)" and confirm the toast's dismiss button is reachable. Investigating that surfaced a real bug, independent of screen readers. | **Bug found and fixed 2026-07-26.** While the edit-task/new-task modal was open, a client-side validation failure fired an error toast whose dismiss button was unreachable — confirmed two ways: `element.focus()` silently no-op, and a raw mouse click at the button's screen coordinates hit the `<dialog>` element instead (`document.elementFromPoint` returned `DIALOG`, not the button). **Root cause:** native `<dialog>` + `showModal()` marks everything else in the document inert, and this is not scoped to non-top-layer content — it also catches other top-layer elements. Verified independent of this app/React entirely with a bare HTML repro (two `<dialog>`/`popover` elements, no framework): a `popover="manual"` element is inert while any `<dialog>` is `showModal()`-open, regardless of which was shown first or which is "on top" in the top-layer stack. **This ruled out the originally-planned fix** (promote the toaster via the Popover API) — verified as a dead end before committing to it, not merely assumed. **Actual fix:** client-side schema-validation failures in `new-task-modal.tsx` and `edit-task-modal.tsx` now render an inline `role="alert"` message inside the still-open dialog instead of calling `toast(..., "error")`. The dialog stays fully interactive — the user just fixes the input and resubmits, no separate dismiss action needed. Global toasts are unaffected for every other path (success, server-side action failures) since those already fire after the modal has closed. Tests added: `new-task-modal.test.tsx` and `edit-task-modal.test.tsx` each assert the inline alert renders, `toast`/the action are not called, and the dialog does not close. |
