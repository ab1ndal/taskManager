**Bug found and fixed during this check:** initially, Space did nothing (no lift, no announcement) and arrow keys scrolled the page instead of moving the item — on every task, in every browser tested, including a fresh incognito window and after a full dev-server restart. Root cause: `@hello-pangea/dnd` refuses to start a drag when the triggering event originates inside a native interactive element (`button`, `input`, `textarea`, etc.) unless `disableInteractiveElementBlocking` is set on `<Draggable>` — our drag handle is a real `<button>` (needed for its own `aria-label` and 44px hit target), and this project never set that prop. The check applies identically to mouse and keyboard, but keyboard's Space is unambiguous with "activate button" so it hit the block outright; mouse-drag reports from testing may have been a false positive from something else moving on screen. Fixed in `src/app/tasks/tasks-page-client.tsx` by adding `disableInteractiveElementBlocking` to the `Draggable`. Confirmed fixed live by re-testing after the change.

**Bug found during this check:** the original test, run against 008's `next_sort_key()`, returned the same value (19000) from both tabs. Root cause turned out not to be a test-methodology artifact — `next_sort_key()` was read-only (`SELECT MAX(...) + 1000`, no write), so calling it twice with nothing inserted between calls could never produce different values regardless of locking. Worse, tracing the real call sites (`src/app/tasks/actions.ts`) showed the advisory lock (`pg_advisory_xact_lock`, transaction-scoped) was released when the RPC's own transaction ended — *before* the app's separate `.insert()` ran. Two concurrent assigns for the same member could both complete their locked read of the same stale `MAX` before either had inserted, landing on the same key. The C3 race was never actually closed by 008. Fixed in migration `009_atomic_assign_task.sql`: `assign_task_member(task_id, member_id)` folds the `MAX` read and the `INSERT` into one statement inside the same lock scope, and `actions.ts` now calls it directly instead of computing a key and inserting separately. `009` is live (deployed via `deploy-migrations.yml`, commit `3527383`). Row 3 needs re-running against the new function before sign-off.
