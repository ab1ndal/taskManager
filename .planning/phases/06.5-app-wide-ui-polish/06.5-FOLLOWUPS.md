# Phase 6.5 — Followups

Raised 2026-07-27, at the end of the second (Playwright, four-browser) verification pass. Nothing
here blocks 6.5 sign-off; all of it is work the pass surfaced and deliberately did not do.

Each item states what is true today, why it matters, and what "done" looks like. Ranked within
sections by how much a user would feel it.

---

## Ship-blocking-adjacent

### F1 — 20 commits sit unpushed on `main`

`git log origin/main..HEAD` is 20 commits, covering this session and the several before it. The
project's convention since Phase 03 is to land on `main` directly, so there is no branch to open a
PR from, but nothing is on the remote either.

**Done:** `git push origin main`, or a decision to keep this local and a note saying so.

### F2 — `npm run test:e2e` writes to the hosted Supabase project

Global setup seeds against the same database that holds real data. Teardown deletes by workspace
name (`e2e-phase65 Household`) and by the two `e2e-phase65@…` user emails, so it is scoped, but:

- two concurrent runs collide — the second run's `seed()` calls `teardown()` first and would delete
  the first run's fixtures mid-test;
- there is no guard against pointing it at a production `.env`;
- wiring it into CI as-is would run it against dev data on every push.

**Done:** a separate Supabase project for tests (or a local `supabase start` stack, currently
blocked on Docker per L9), plus a refusal in `e2e/fixtures.ts` if the target URL is not the
designated test project.

## Correctness and consistency

### F3 — Subtask delete has no confirmation

Deleting a task goes through `ConfirmDialog`. The subtask trash button added to the edit modal in
`4f35901` deletes on the first click. Same destructive weight, two different rules, and the phase
6.5 audit specifically raised "Confirmation Dialogs (High)" as the reason leaving a workspace got
one.

**Done:** subtask delete routes through `ConfirmDialog`, or a written decision that a subtask is
cheap enough to delete unguarded (it is not — it can carry its own description and due date).

### F4 — `RowMenu` has no arrow-key navigation

It renders `role="menu"` with `role="menuitem"` children, so assistive tech announces a menu and a
user reasonably expects Up/Down to move between items. Only Tab does. Escape, outside-click dismissal
and focus-return to the trigger all work and are covered by `e2e/dialogs.spec.ts`.

**Done:** either implement roving focus per the ARIA APG menu pattern, or drop the `menu`/`menuitem`
roles and render it as a plain group of buttons, which is honest about what it is.

### F5 — Subtask fields are asymmetric between the two modals

The new-task modal gives each subtask a title, details and a due date. The edit modal takes a title
only. `addSubtask` already accepts `description` and `dueAt` — this is UI, not server work. A subtask
created during task creation can therefore hold data that can never be edited afterwards, and one
added later can never be given that data at all.

**Done:** the edit modal's add-subtask row matches the new-task modal's, and existing subtasks are
editable.

### F6 — Reopening a parent leaves its subtasks completed

Deliberate, documented in `actions.ts` and covered by a unit test: the subtask work was genuinely
done, and whatever reopened the parent is new work. Worth watching in real use — reopening "take the
bins out" leaves both its subtasks ticked, which may read as wrong to someone who expected a reset.

**Done:** confirmed in use, or changed with a stated reason. Not a bug today.

## Verification gaps the new suite does not close

### F7 — Drag-to-reorder has zero end-to-end coverage

No spec in `e2e/` exercises it, in any browser. It is the one interaction that is pure pointer and
touch behaviour — precisely what jsdom cannot reach and what the harness now can. `@hello-pangea/dnd`
is driven by real sensors; the existing unit tests call `buildDragEndHandler` directly with a
fabricated `DropResult`, which verifies the key arithmetic and nothing about whether a drag can be
started. Touch drag on the iPhone profile is entirely unverified.

**Done:** a spec that drags a row within a bucket in Chromium and on the iPhone profile, asserts the
new order survives a reload, and asserts the keyboard path (focus handle, Space, Arrow, Space).

Highest-value item in this section.

### F8 — Contrast and dark mode are measured on `/tasks` only

`e2e/theming.spec.ts` walks every text node on the tasks page in both schemes. It never visits
`/workspaces`, `/profile` or `/login`, and never runs with a dialog open — which is where
`--color-surface-sunken` and the status tokens actually get used.

**Done:** the same walk, parameterised over the four routes and over "dialog open".

### F9 — No screenshot baselines

Every assertion is about a measured property. A layout that drifts without violating one still ships
clean. The five defects the first visual pass caught were all found by a human looking at a picture.

**Done:** `toHaveScreenshot()` baselines for the task list, both modals and the workspace card, in
both schemes, at desktop and iPhone widths.

### F10 — Dictation and microphone-permission denial still need a human

Unchanged from Phase 06. Chromium's fake-device flags do not drive the Web Speech API — it is a cloud
service in Chrome and absent in Firefox — so `06-VERIFICATION.md`'s dictation checks cannot be
automated with this harness.

**Done:** run by hand in Chrome and Safari, once, and record the result.

## iPhone deliverable

### F11 — The installed app has no offline support

There is no service worker, so a home-screen launch needs the network for every load, including the
app shell. If "local distribution" is meant to survive a plane or a lift, that is real work — a
service worker with a precached shell and a considered stale-while-revalidate policy for task data,
plus a story for writes made offline.

**Done:** decide whether offline is in scope. If yes, it is its own slice, not a config flag.

### F12 — The icons are placeholder art

`public/icons/*` and `src/app/{icon,apple-icon}.png` are generated flat PNGs: accent purple, the
geometric check the empty state draws. Correct sizes, correct maskable safe zone, no brand.

**Done:** real artwork at 192, 512, maskable 512 and 180.
