## Correctness and consistency

### F3 — Subtask delete has no confirmation — CLOSED (`09b6dda`)

The subtask trash button routes through `DeleteConfirmDialog`, the same shell task delete uses. The
confirmation is a second `showModal()` nested inside the open edit modal: it stacks above it in the
top layer, so Escape dismisses only the confirmation. Covered by three tests in
`src/app/tasks/edit-task-modal.test.tsx`.

### F4 — `RowMenu` has no arrow-key navigation — CLOSED (`bed3fa8`)

Implemented rather than dropped: roving focus per the ARIA APG menu-button pattern. The menu is a
single tab stop, Up/Down wrap, Home/End jump to the ends, ArrowUp on the trigger opens with the last
item focused, and Tab leaves the menu. Escape, outside-click dismissal and focus-return to the
trigger are unchanged. Covered by `src/components/__tests__/row-menu.test.tsx` (7 tests).

### F5 — Subtask fields are asymmetric between the two modals — CLOSED (`d5cc3eb`)

The edit modal's add-subtask row now carries title, details and due date, matching the new-task
modal. Existing subtasks render their details and due date, and a pencil opens them for editing
through a new `updateSubtask` action — it edits only the three fields the subtask UI owns and leaves
assignment alone, since a subtask inherits its assignees from its parent. The subtasks query and
`RawTask` now carry `description` and `due_at`.

### F6 — Reopening a parent leaves its subtasks completed — CLOSED (2026-07-27)

Deliberate, documented in `actions.ts` and covered by a unit test: the subtask work was genuinely
done, and whatever reopened the parent is new work.

Confirmed by hand in the running app on 2026-07-27 — the behaviour reads correctly in use, so the
rule stands as written and no reset is added.

## Raised by the F10 manual run (2026-07-27)

### F15 — The dictation textarea does not scroll while dictating — CLOSED (`58d8dfe`)

Every dictatable field now scrolls to its newest text for as long as it holds the session
(`src/components/dictation-textarea.tsx`). The cause was that dictation replaces the whole value on
every interim result, which never moves the caret, so the browser has no reason to scroll.

### F16 — Dictation is available on updates only — CLOSED (`58d8dfe`)

The task description (both modals) and every subtask description (the new-task rows, the edit
modal's add row, and an existing subtask opened for editing) now carry the same mic as the update
composer.

`useDictation` (`src/lib/use-dictation.ts`) owns one session that a field claims by id; claiming it
stops whatever held it, so two recognizers never overlap. A terminal error is reported under the
field that was dictating rather than floating loose in the form. `DictationTextarea` puts the mic
inside the field — borderless, inset clear of the border — so it drops into any layout.

One thing the first cut got wrong: the subtask mic was labelled "Dictate subtask 1 details", which
contains the field's own label, and any substring-matching label query then resolved to two
elements. `e2e/dialogs.spec.ts` caught it. Labels now read "Dictate details for subtask 1".

### F16 — original statement

The mic is wired to the update composer alone. The task description (both the new-task and the
edit-task modal) and the subtask description (both the add row and the inline edit row) are plain
textareas, which is where a spoken sentence is most useful.

One recognizer may be live at a time, so this is not four independent hooks — it needs a single
shared session with an owning field, and a `stop()` whenever focus or the owner changes.

**Done:** the same dictation control on the task and subtask description fields, with only one
field able to hold the session.

### F17 — Updates outrank Subtasks in the modal, and their timestamps are relative-only — CLOSED (`58d8dfe`)

Subtasks now render above Updates, the update list dropped its `max-h-40` inner scroller and grows
with the modal body, and each update's relative label carries the exact date and time in its
`title` via a new `formatUpdateTimestamp`. Screenshot baselines regenerated for the new order.

### F17 — original statement

Updates render first (`mt-6`), Subtasks second, and the update list is its own `max-h-40`
inner scroller. Subtasks are the structure of the task and belong directly under its fields;
updates are a log and read better as the tail of the modal, scrolling with the modal body rather
than inside a 160px window nested in a scrollable dialog.

`formatUpdateTime` (`edit-task-modal.tsx:39`) emits "just now", "12m ago", "3h ago" then a bare
"Jul 12" — the exact date and clock time are nowhere, so an update older than a day cannot be
placed in time.

**Done:** Subtasks above Updates; the update list scrolls with the modal, not inside its own box;
each update carries an exact date and time (relative label kept, absolute available).

### F18 — A task card opens its modal only through the row menu — CLOSED (2026-07-27)

Pressing anywhere on a card that is not already a control opens the same edit modal. The complete
toggle stays a one-press complete, on the task and on each subtask, which was the explicit
requirement — the quick tick is the card's most-used gesture and it keeps working untouched.

One guard rather than a `stopPropagation` on every control
(`src/components/task-card.tsx`): the handler returns early for any event that started inside a
`button`, `a`, `input`, `label` or `dialog`, and for any event already `defaultPrevented` — which
is how a completed drag announces itself, so dropping a card does not open it. The `dialog` case is
not theoretical: the delete confirmation renders inside the card's own subtree, so its Cancel
button would otherwise have opened the modal on the way out.

No `role`/`tabIndex` on the card. A keyboard user reaches the same modal through the pencil above
`sm` and the row menu below it; turning a container that holds four buttons into a button itself
would nest interactive elements rather than fix anything. Completed cards get no handler and no
pointer cursor, matching the existing rule that a completed task has no edit.

Covered by six tests in `src/components/__tests__/task-card.test.tsx`.

### F18 — original statement

`onEdit` is passed to `RowMenu` alone (`tasks-page-client.tsx:384`), so opening a task is a
two-step, menu-first gesture — unusual for a list where the row is the object. The card already
holds three interactive controls (the complete checkbox, the drag handle, the menu button), so a
naive card-level `onClick` would both swallow their clicks and create a click target that keyboard
users cannot reach without nesting interactive elements.

**Done:** a task can be opened from the card itself, by pointer and by keyboard, without breaking
the checkbox, drag handle or menu.

### F19 — Updates and newly created tasks take 1–2s to become real — OPEN

Two separate lags, both observed in `next dev`:

- opening a task fetches its updates on open (`getTaskUpdates`, `edit-task-modal.tsx:107`) with no
  pending state, so the empty branch renders "No updates yet" until the round trip lands;
- creating a task renders an optimistic ghost at 40% opacity that is neither editable nor
  draggable until `revalidatePath("/tasks")` returns a real row.

Neither has been measured against a production build, where Turbopack's per-route compile is gone.
That measurement comes first — the fix differs completely if the real number is 150ms.

**Done:** measured on `npm run build && npm start`; if the lag is real, the empty state stops
lying during the fetch and a fresh task is usable before the server round trip completes.

## Raised 2026-07-27, outside the 6.5 pass

### F20 — Signup confirmation email never arrives on the production URL — CLOSED 2026-07-27

**Root cause found, and it was not SMTP.** The report came from signing up again with an
already-registered address. Supabase answers that with an obfuscated user object and `error === null`
— no email is sent at all, deliberately, so the form cannot be used to discover which addresses have
accounts. The old code read `error === null` as success and toasted "Check your email to confirm your
account", so the user waited for mail that was never sent and had no route to recovery. Confirmed
against the Supabase JS spec, not inferred.

Fixed in `src/app/login/login-card.tsx`:

- Duplicate signups are detected via the empty `data.user.identities` array and now show "That email
  already has an account" with **Sign in** and **Reset your password** buttons. This intentionally
  reveals that the address is registered. The enumeration trade-off was raised and accepted by the
  owner on 2026-07-27 — a personal household app, and the alternative stranded the user. The
  `identities` signal is not part of the documented API contract; if an auth-js upgrade stops
  emptying it the branch goes quiet and the generic "check your email" message returns. Commented at
  the call site.
- `emailRedirectTo` is now passed explicitly. Without it the link inherited the project's Site URL —
  the app root, where nothing exchanges the `code`, so even a delivered link landed the user signed
  out. Site URL and the `/auth/callback` redirect allow-list entry were set in the production
  dashboard the same day.

`/auth/callback` needed no change — it handles both the PKCE `code` and `token_hash` shapes.

**Closed** by the owner on 2026-07-27 after confirming the flows work on production. The built-in
SMTP limitation was carved out to **F22** rather than closed with this item — it was never the cause
of this report, and a fresh non-team-address delivery was not observed end to end.

### F21 — No Google sign-in — CLOSED 2026-07-27

Owner completed the out-of-repo half on 2026-07-27: Google Cloud OAuth client (authorised redirect
URI `https://<project-ref>.supabase.co/auth/v1/callback`), client id and secret in Supabase's Google
provider, Vercel URL in the Auth redirect allow-list.

Client side is in `src/app/login/login-card.tsx`: a "Continue with Google" button, shown in signin and
signup modes only, calling `signInWithOAuth({ provider: "google" })` with
`redirectTo=<origin>/auth/callback?next=/tasks`. `/auth/callback` already exchanges the returned
`code`, and `resolve-next.ts` accepts `/tasks`, so no route change was needed. `profile/page.tsx:19`
reads `user_metadata.name`, which Google populates — display names work with no migration.

Note there is no `supabase/config.toml` in this repo, so the local stack has no Google provider
configured. Google sign-in can only be exercised against a deployed environment; adding local support
means a `config.toml` plus a second Google client, and is deliberately out of scope.

**Closed** by the owner on 2026-07-27: Google sign-in completes on production and lands on `/tasks`.
Note that a Google signup and a Google sign-in are the same call — Supabase creates the user on the
first return from the provider and links it to any existing account with the same confirmed email, so
there is no separate signup path to build.

### F22 — Production email delivery is limited to project-team addresses — OPEN

Split out of F20 on 2026-07-27. The project still uses Supabase's built-in SMTP, which is rate-limited
to roughly two messages an hour and, under current project defaults, delivers only to addresses on the
project team. Any other recipient gets silence, with the failure visible only in the Auth logs.

Nothing in the app is wrong — this is a project configuration limit. It has never been exercised
successfully: no signup or password reset to a non-team address has been observed arriving.

Google sign-in routes around it entirely, since Google has already verified the address and no
confirmation mail is sent. So this only blocks email-and-password signup and password reset for
anyone outside the team.

**Done when:** custom SMTP (Resend, Postmark, or similar) is configured in the Supabase dashboard, and
a signup and a password reset to a non-team address both arrive.

### F23 — A missing server config fails as a per-request "Something went wrong" — CLOSED (accepted) 2026-07-27

Raised and closed the same day. `createAdminClient()` (`src/lib/supabase/admin.ts`) throws when
`SUPABASE_SECRET_KEY` is absent. `run()` in `src/app/tasks/actions.ts:75` genericises that into
"Something went wrong. Please try again", and `/workspaces` surfaced it as a bare Next.js error digest,
so a deployment misconfigured from the moment it shipped looked like a flaky app.

**Decided: the behaviour stays as it is.** `run()` passes validation and authorization messages through
to the user and genericises everything else, which is the right default — database errors carry schema
detail the client has no business seeing. It also already logs the real cause as structured JSON at
`actions.ts:68`, and that log line is what named the missing variable during the outage. The
information was never absent; nobody was reading it. A boot-time env check was considered and
declined as not worth the code.

**If this bites again:** `vercel logs <domain>` first. The digest in the browser is meaningless on its
own, and the log line states the cause outright.

**Context — the outage that exposed it:** the 2026-07-25 rename from
`NEXT_PUBLIC_SUPABASE_SECRET_KEY` to `SUPABASE_SECRET_KEY` was applied to the code and to
`.env.local`, but not to Vercel, where the variable stayed under the old name on Production, Preview
and Development. Every admin-client path — `/workspaces` and all twelve `createAdminClient()` call
sites in `actions.ts` — threw from that deploy onward. Fixed on 2026-07-27 by adding
`SUPABASE_SECRET_KEY` in Vercel, removing the `NEXT_PUBLIC_`-prefixed variable, and redeploying; the
key was rotated because it had carried a browser-exposing prefix for 119 days. A scan of the client
chunks served by `/login` found no leaked secret, but that sample does not cover deploys made before
the rename.

**Done when:** a missing or empty `SUPABASE_SECRET_KEY` produces one unmistakable error naming the
variable, instead of a generic failure on every mutation.
